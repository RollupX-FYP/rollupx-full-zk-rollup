
\section{Analytical Cost Model}
\label{sec:cost_models}

The empirical benchmarking framework uses static configuration sweeps to study cost behaviour under controlled conditions. Although early project proposals discussed dynamic batching cost models, where the system would estimate an optimal batch size based on changing Layer-1 base fees, this dynamic optimization logic is not implemented in the active runtime codebase. Instead, the implemented system records gas, data availability, and submission telemetry for each benchmark configuration and applies an analytical cost model during result analysis.


Following the cost decomposition used by Chaliasos et al.~\citep{chaliasos2024analyzing} and data availability analysis by Saif et al.~\citep{saif2024dataavailability}, the model separates rollup costs into fixed batch costs and marginal transaction costs. Fixed costs are incurred once per batch and are amortized across all transactions in that batch. Marginal costs increase with the number or size of transactions, such as data availability bytes, witness generation, execution effort, and proving overhead.

The basic cost relationship used in the analysis is shown in Equation~\ref{eq:cost_per_tx}. It captures the main rollup trade-off: increasing the batch size reduces the fixed cost per transaction, but it can also increase queueing latency because transactions may wait longer before the batch is sealed.

\begin{equation}
\label{eq:cost_per_tx}
\begin{aligned}
\text{Cost per transaction}
&=
\frac{
\text{fixed batch settlement cost} + \text{proof verification cost}
}{
\text{batch size}
}
\\
&\quad + \text{marginal DA cost per transaction}
\end{aligned}
\end{equation}




In the implemented benchmarking stack, the cost model is evaluated using runtime telemetry generated by the Submitter and later processed by the analytics pipeline. The default static environment assumptions are \texttt{ETH\_PRICE\_USD = 2500}, \texttt{REGULAR\_GAS\_PRICE\_GWEI = 2.0}, and \texttt{BLOB\_GAS\_PRICE\_GWEI = 0.001}. These values are used when measured runtime values are unavailable. As a result, USD-denominated costs are treated as explanatory estimates, while gas units and Wei-denominated values are used as the more stable basis for cross-configuration comparison.

For regular Layer-1 gas, the implementation computes cost by multiplying the measured \texttt{regular\_gas\_used} by a selected gas price reference. If a valid measured runtime gas price is available, the measured value is used. Otherwise, the configured reference gas price is used. For blob-based data availability, blob cost is applied only when the selected DA mode is blob. If the benchmark run uses a real EIP-4844 blob transaction and measured blob gas values are available, the implementation uses measured blob gas and blob gas price. If real blob gas measurements are not available, the model uses estimated blob gas usage instead.

The implementation classifies cost values according to their source. A \texttt{measured} cost source indicates that the required runtime gas values were available. A \texttt{hybrid} source indicates that regular gas was measured but blob gas was estimated. An \texttt{estimated} source indicates that reference assumptions were used because measured values were unavailable. This distinction is important because it prevents simulated blob experiments from being interpreted as fully measured EIP-4844 results.

The Python aggregation pipeline summarizes these batch-level values into run-level metrics such as average total cost, average cost per transaction, average regular gas used, average blob gas used, and average USD cost estimate. However, because ETH price and gas prices fluctuate in real networks, the primary comparison in this study is based on gas units, data availability bytes, and cost per transaction in Wei. These metrics provide a more stable basis for evaluating the relative efficiency of different batching and data availability configurations.
