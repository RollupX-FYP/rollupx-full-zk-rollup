
\section{Workload Model}
\label{sec:workload_model}

The benchmarking methodology uses controlled synthetic workloads to isolate the effect of system configurations from external noise. Instead of replaying historical mainnet traces, the experiments generate repeatable transaction traffic under known input conditions. This approach allows performance changes to be attributed more directly to configuration choices such as batch size, batch timeout, sequencing policy, prover mode, and data availability mode.

The workload is generated using a Python-based \texttt{poisson\_generator.py} script. The generator produces transaction arrivals using a seeded Poisson process, which approximates steady-state user traffic while preserving reproducibility across repeated benchmark runs. The main configurable workload parameters include the offered input rate in transactions per second, benchmark duration, warm-up duration, random seed, sender concurrency, transaction mix, and burst-traffic settings. Warm-up traffic is sent before the timed measurement period but is excluded from the final metrics, allowing the system to reach a more stable operating state before data collection begins.

Figure~\ref{fig:workload_generation_model} summarizes the workload generation process used in the benchmark suite. The model begins with a controlled experiment configuration, generates seeded transaction arrivals, selects transaction classes according to the chosen mix preset, and submits the generated transactions to the Sequencer. The same generator also records workload-side metrics so that submitted transaction counts, latencies, success rates, and offered rates can be analyzed after each run.

The workload generator supports three abstract transaction classes. These classes are not intended to fully reproduce arbitrary EVM execution. Instead, they provide controlled transaction profiles with different gas limits, gas prices, calldata sizes, and data availability footprints. This makes it possible to evaluate how transaction heterogeneity affects batching, sequencing, proving, and L1 submission behavior.

Several transaction mix presets are used to generate different workload regimes. The \textit{transfer} preset isolates simple transfer behavior, while the \textit{balanced} preset provides a mixed baseline. The \textit{heavy} and \textit{da\_heavy} presets increase the proportion of larger transactions to stress the prover and data availability paths. Custom mixes can also be defined using explicit fractions for Type A, Type B, and Type C transactions.

In addition to steady-state traffic, the generator supports burst-mode experiments. Burst tests are implemented by alternating between a base transaction rate and a higher peak rate using configurable burst period and duty-cycle parameters. For example, the workload can maintain an 8 TPS base rate and periodically inject an 80 TPS burst. This does not fully capture the complexity of extreme DeFi events, but it provides a controlled way to test queue buildup, adaptive batching behavior, and recovery after temporary load spikes.

\subsection{Use of Local Hardhat Node and Mock Prover}
\label{subsec:hardhat_mock_prover}

A key methodological choice in this project is the use of a local Hardhat node and a mock prover for most benchmark sweeps. This choice improves experimental control and prevents external infrastructure variability from hiding the behavior being measured.

\begin{itemize}
    \item \textbf{Local Hardhat node:} 
    The Layer-1 settlement environment is executed on a local Hardhat node. This removes public-network noise such as fluctuating gas prices, validator delays, mempool congestion, and unpredictable finality variance. As a result, the experiments can focus on the behavior of the Layer-2 pipeline, particularly batching, sequencing, submission, and data availability formatting.

    \item \textbf{Mock prover:} 
    Real cryptographic proving, especially using zkVM-based systems such as RISC0, is computationally expensive and can dominate benchmark results. If real proving is used in every experiment, it becomes difficult to observe smaller queueing and scheduling effects in the sequencer and submitter. Therefore, the main benchmark stages use a mock prover with parameterized delay to model proof-generation overhead in a controlled way. Real RISC0 proving is evaluated separately in dedicated experiments to study cycle behavior and prover-specific limits.
\end{itemize}

To ensure that the load generator can saturate the Sequencer without becoming the bottleneck, the benchmark stack can use unsigned or pre-signed user transactions when \texttt{ALLOW\_UNSIGNED\_USER\_TXS} is enabled. This reduces client-side signing overhead during high-rate benchmark runs and helps keep the focus on the rollup pipeline rather than on workload-generation cost.

The workload model is therefore intentionally controlled rather than fully realistic. Its purpose is to provide repeatable experimental inputs that make configuration-level comparisons meaningful. This supports the main objective of the project: to evaluate how batching, sequencing, proving, and data availability choices influence ZK-rollup throughput, latency, finalization time, and cost.
