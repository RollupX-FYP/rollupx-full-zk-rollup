\subsection{Data Availability Modes}
\label{subsec:data_availability_modes}

Data availability is a central design variable in rollup systems because it determines where transaction data is published and who can reconstruct the rollup state if needed. In this project, data availability is treated as a configurable benchmarking dimension rather than as a production-grade security mechanism. The goal is to compare how different DA choices affect payload size, Layer-1 submission cost, and finalization behaviour under the same workload conditions.

Figure~\ref{fig:da_modes_taxonomy} summarizes the data availability modes considered in this study. The prototype distinguishes between on-chain data availability, where transaction data or data commitments are submitted to Layer 1, and off-chain data availability, where the batch data is stored outside the base chain under additional trust assumptions.

The methodology evaluates two primary Layer-1 data availability modes and includes one simulated off-chain mode for comparison.

\begin{itemize}
    \item \textbf{Calldata mode:} 
    In calldata mode, the compressed transaction payload is submitted as standard Layer-1 transaction input data. This provides strong Ethereum-level data availability because the data is directly published on Layer 1. However, it can be expensive because calldata contributes directly to Layer-1 gas usage.

    \item \textbf{EIP-4844 blob mode:} 
    In blob mode, the batch payload is formatted as blob data and submitted through an EIP-4844-style blob-carrying transaction. The corresponding commitment is available to Layer 1, while the blob data is stored separately for a limited availability window. This mode is used to evaluate how blob-based submission affects DA cost and payload efficiency compared with calldata.

    \item \textbf{Local off-chain DA stub:} 
    The prototype also includes a local off-chain DA stub to model a validium-like configuration under controlled conditions. This mode does not represent a real integration with external DA systems such as Celestia, EigenDA, or IPFS. Instead, it is used only as a research configuration to compare the effect of moving batch data outside the Layer-1 calldata or blob path.
\end{itemize}

These modes allow the experiments to compare the trade-off between cost, data footprint, and trust assumptions. Calldata provides the strongest and simplest Layer-1 availability model but has higher cost. Blob-based submission reduces the cost of publishing large batch payloads by using the blob data path. The local off-chain DA stub provides a low-cost reference point but weakens the security assumptions because data availability is no longer guaranteed directly by Ethereum. Therefore, the DA mode is treated as a major configuration variable in the benchmarking methodology.
