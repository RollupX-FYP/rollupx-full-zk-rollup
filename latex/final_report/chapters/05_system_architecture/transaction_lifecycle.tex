\section{Transaction Lifecycle and Data Flow}

Figure~\ref{fig:tx_lifecycle} provides an overview of the transaction lifecycle.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.90\textwidth]{figures/chapter3/tx_lifecycle.png}
    \caption{Transaction Lifecycle.}
    \label{fig:tx_lifecycle}
\end{figure}
\label{sec:transaction_lifecycle}
The transaction lifecycle spans both the data plane (handling transaction execution) and the control plane (handling orchestration and metric collection). The end-to-end flow is detailed below.

\begin{enumerate}
    \item \textbf{Ingestion (Workload Generator):} A Python-based synthetic Poisson Workload Generator synthesizes transaction payloads (primarily ERC-20 style transfers) and submits them to the Sequencer.
    \item \textbf{Sequencing and Batching (Sequencer):} The Sequencer, implemented in Rust, validates the transactions and holds them in a local transaction pool. It orders them according to the configured scheduling policy (e.g., FCFS, FeePriority, or TimeBoost). A background Batching Engine evaluates triggers (such as maximum batch size or a timeout interval). Once a trigger condition is met, the batch is "sealed" and dispatched. This phase establishes \textit{soft finality}, providing immediate confirmation to users that their transaction is scheduled.
    \item \textbf{Execution (Executor):} The Executor, also written in Rust, receives the sealed batch via a gRPC stream. It applies the transactions against its local canonical state representation (updating account balances and nonces via a Sparse Merkle Tree) and computes the new global state root.
    \item \textbf{Proving (Prover Subsystem):} The Executor delegates proof generation to the Prover. For high-volume benchmarking, a \textit{mock prover} introduces parameterized delays, simulating computational overhead without bottlenecking on hardware. For cycle-analysis experiments, a real \textit{RISC0 prover} backend is utilized, executing the state transitions within the zkVM to generate authentic STARK proofs, which are subsequently compressed into Groth16 proofs.
    \item \textbf{Submission (Submitter):} The Submitter (Rust) acts as the bridge between L2 and L1. It listens to the Executor's gRPC stream, packages the execution results, the proof, and the transaction data into a final payload. Crucially, the Submitter's Data Availability Formatter structures the data according to the selected DA mode (e.g., standard \texttt{calldata}, EIP-4844 blobs, or off-chain stubs) and manages the retry logic via a Saga Workflow.
    \item \textbf{L1 Settlement (Smart Contracts):} The Submitter broadcasts the transaction to the L1 Smart Contracts running on a local Hardhat node. The L1 contract verifies the DA commitments and the proof using either a Mock Verifier (for benchmark mode) or a real Groth16 Verifier (for RISC0 mode), subsequently updating the on-chain canonical state root. This finalizes the transaction, establishing \textit{hard finality}.
\end{enumerate}

Throughout this lifecycle, a metrics pipeline continuously logs telemetry data. This data is later processed by the Data Tools (e.g., \texttt{aggregate.py} and \texttt{stats.py}) to generate the performance analyses presented in this report.
