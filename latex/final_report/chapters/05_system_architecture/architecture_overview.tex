\section{High-Level Architecture Overview}
\label{sec:architecture_overview}

The prototype developed in this project separates the standard ZK-rollup pipeline into a set of distinct, containerized microservices. This modular architecture is designed primarily as a research-grade benchmarking framework rather than as a production deployment. Its purpose is to make the internal stages of a ZK-rollup pipeline observable, configurable, and independently testable under controlled experimental conditions.

The end-to-end execution flow begins with the Workload Generator, which produces controlled synthetic transaction traffic. These transactions are then submitted to the Sequencer, where they are validated, ordered, and grouped into batches. The sealed batches are forwarded to the Executor, which applies the state-transition logic and produces updated state commitments. Depending on the benchmark configuration, the Prover generates either mock proof artifacts or RISC0-based proof outputs. Finally, the Submitter formats the data availability payload and submits the verified state update to the Layer-1 smart contracts.

This structure is intentionally simpler than a production ZK-rollup. The goal is not to reproduce every feature of systems such as zkSync Era, Scroll, Starknet, or Polygon zkEVM. Instead, the goal is to provide a compact and controllable research tool. Each stage is separated so that a specific design factor, such as batch size, sequencing policy, prover delay, or data availability mode, can be changed while keeping the rest of the experimental environment stable.

The logical execution flow of this modular benchmarking framework is summarized in Figure~\ref{fig:end_to_end_execution_flow}.

Each component in Figure~\ref{fig:end_to_end_execution_flow} represents a separately observable stage of the benchmarking pipeline. The Workload Generator controls the input traffic pattern, allowing the same workload model to be reused across different experimental configurations. The Sequencer is responsible for transaction validation, ordering, and batch formation. The Executor applies the simplified state-transition function and produces updated state commitments. The Prover stage models the proof-generation bottleneck using either benchmark-mode delay or RISC0-based proving. The Submitter bridges the executed batch to Layer 1 by preparing the proof output, data availability payload, and state update.

The system also collects telemetry from each major stage of the pipeline. Raw JSON and CSV metrics are produced by the Sequencer, Executor, Submitter, and workload tools. These metrics are later processed by the Data Tools pipeline for aggregation and analysis. Local execution is orchestrated using \texttt{docker compose} profiles, allowing the core stack, benchmark generator, and reporting tools to be started independently. By decoupling validation, batching, execution, proving, submission, and metrics collection, the prototype enables controlled experimentation on variables such as batch size, sequencing policy, prover delay, and data availability mode.

\subsection{Prototype vs. Production Rollup Comparison}
\label{subsec:prototype_vs_production}

It is important to distinguish the proposed research prototype from a production ZK-rollup. Production rollups such as zkSync Era, Scroll, Starknet, and Polygon zkEVM are designed for real user deployment. They require full or near-full Ethereum Virtual Machine compatibility, complex validity-proof pipelines, large-scale state management, robust sequencer infrastructure, censorship-resistance mechanisms, and strong liveness and safety guarantees in adversarial environments.

In contrast, the prototype developed in this project is intentionally scoped as a research-grade benchmarking framework. It does not attempt to implement a full zkEVM or compete with production rollups. Instead, it implements a simplified transfer-centric state-transition engine suitable for controlled benchmarking. This design choice reduces implementation complexity while still preserving the key stages required to study rollup performance: sequencing, batching, execution, proving, data availability formatting, and Layer-1 submission.

The prototype runs in a controlled, non-Byzantine local Hardhat environment. Data availability is evaluated through calldata, EIP-4844 blob-based submission, and a local off-chain DA stub. The off-chain DA mode is used only as a simulated research configuration and does not represent a complete integration with external data availability networks such as IPFS, Celestia, or EigenDA.

This focused scope is central to the project's contribution. By avoiding the engineering overhead of a production-grade rollup, the framework allows researchers to isolate and measure the effect of individual configuration choices. For example, batch size limits, timeout values, scheduling policies, prover modes, and data availability modes can be varied under the same synthetic workload. This makes the prototype useful as a reproducible research tool for analyzing throughput, latency, finalization time, proving overhead, and cost trade-offs in ZK-rollup systems.
