## 5. Submitter Service Contribution

### 5.1 Submitter Architecture

I established the main execution structure for the Submitter daemon, focusing on a clean Domain-Driven Design (DDD) layout.
*   **Evidence:** Added `submitter/src/application/orchestrator.rs` and removed duplicate legacy implementations (`src/main.rs`, `src/submitter.rs`) in commit `e4dad07`.
*   **Technical Value:** The Orchestrator safely polls the Executor for new batches, pulls proofs, and drives the reliable submission process.

### 5.2 BridgeClient and Ethereum Adapter

To enable robust testing without relying on live Ethereum networks, I abstracted the L1 interaction logic.
*   **Evidence:** Created `submitter/src/infrastructure/ethereum_adapter.rs` and introduced the `BridgeClient` trait (Commit: `e4dad07`).
*   **Technical Value:** Allowed DA strategies to interact with a standard interface rather than concrete `ethers::Provider` types, paving the way for mock-based unit testing.

### 5.3 Data Availability Strategy Implementations

I implemented the concrete DA strategies that encode and post batch data to the L1.
*   **Evidence:** Implemented `submitter/src/infrastructure/da_calldata.rs` and `submitter/src/infrastructure/da_blob.rs`. Added `da_offchain.rs` for validium setups.
*   **Technical Value:** These files implement the logic to format payload sizes. `da_blob.rs` constructs EIP-4844 transactions, while `da_calldata.rs` formats raw hex for standard L1 calldata insertion.

### 5.4 L1 Submission and Receipt Handling

### 5.7 Submitter Testing and Mocking

### 5.8 Submitter Bug Fixes

*   **Evidence:** In `e4dad07`, I fixed silent transaction revert failures on the L1. Previously, the submitter only checked if a transaction was mined. In `da_calldata.rs` and `da_blob.rs`, I introduced explicit checks:
    ```rust
    if let Some(status) = r.status {
        if status.as_u64() == 1 {
            // success
        } else {
            warn!("Tx {} reverted!", tx_hash);
            return Err(DomainError::Da("Transaction reverted on-chain".to_string()));
        }
    }
    ```
*   **Technical Value:** Prevented the orchestrator from incorrectly marking failed L1 settlements as successful.

## 11. End-to-End Integration Contribution

My work fundamentally connected the entire pipeline:
1.  **Workload Generator** (`poisson_generator.py`) generates load based on `experiments.toml`.
2.  **Sequencer & Executor** (running via `run_experiment.sh`) process transactions and form batches.
3.  **Submitter** (`orchestrator.rs`) picks up the batch and routes it through the appropriate DA strategy (`da_blob.rs`).
4.  **L1 Contracts** (`ZKRollupBridge.sol`, `BlobDA.sol`) receive and verify the payload on the testnet.
5.  **Data Tools** (`aggregate.py`) collects logs from the shared `metrics/` volume and produces output graphs (`latency_cdf.png`).
